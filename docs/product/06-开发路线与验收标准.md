# 开发路线与验收标准

> 状态：执行指南
>
> 更新日期：2026-08-24
>
> 工程基线：PR #7 合并提交 `c734b30`

## 1. 交付原则

- 按完整纵向切片交付，不先堆页面或抽象层。
- 每个切片先在 `admin/` 中确认流程和状态，再完成服务端事实、正式 API、`entry/` 接入和异常恢复。
- 首先实现一份资料的一本学习书，不提前扩展多资料知识空间。
- 设计确认、代码存在、测试通过和真实端到端验证使用不同状态。
- 不继续扩张被新口径取消的独立学习、验证、完成和全局地图页面。

## 2. 里程碑

### M0：文档与合同冻结

目标：所有团队成员对对象、页面和状态使用同一名称。

交付：

- 本目录七份现行产品文档；
- 学习项目聚合 DTO；
- 来源锚点、后台任务、Chat 作用域、学习事件和证据的版本化合同；
- `TodayRecommendation` 与 `ProjectNotice` 的分离合同；
- 服务端合同测试与 ArkTS 客户端测试使用的同形夹具。

验收：旧文档已归档；新代码评审能明确引用现行文档；`entry/` 不复制服务端最终业务规则；`admin/` 的临时 DTO 不被当作正式 API。

M0 只固定领域对象、状态、错误、幂等和版本策略。具体端点按后续纵向切片逐批冻结，不在这一阶段一次性定死。

### M1：创建项目与首章可读

目标：真实用户从一份资料进入可读第一章。

交付：

- PDF、Markdown、DOCX 导入；
- 学习目标、当前水平、学习深度设置；
- 方案生成、编辑和确认；
- 第一章优先生成，其他章节后台排队；
- 学习库项目卡片和项目通知；
- 中断、重试和恢复。

验收：`entry + server` 使用三种真实资料分别成功；首章就绪前后都可离开并恢复；后续章节失败不阻塞首章；重启 `entry/` 后仍能恢复同一项目状态。

### M2：单一学习书工作区

目标：用户在一个工作区完成阅读、来源核查和章节导航。

交付：

- 正文/概念图模式骨架；
- 桌面章节侧栏和手机章节抽屉；
- 六类正式内容块；
- 来源查看器与精确返回；
- 阅读位置、书签和草稿恢复；
- 取消旧的平行讲解、验证和完成主路由。

验收：从任意引用往返不丢位置；手机端正文无固定拥挤分栏；部分生成和失败状态不覆盖已有内容；键盘、返回和覆盖层行为一致。

### M3：有作用域的 Chat

目标：用户能在当前项目和章节内获得可溯源帮助。

交付：

- 学习概况、项目、章节、概念和选中文本作用域；
- 按项目组织的会话历史；
- 流式回答、停止、重试和恢复；
- 引用与“补充说明”标记；
- 写操作确认卡片；
- 章节切换时的作用域确认。

验收：切换章节不会污染旧会话；资料问题能回到原文；无依据时不伪造引用；普通 Chat 无法改变掌握状态。

### M4：学习事件、证据与复习

目标：测验和费曼讲述形成可信、可解释、可重建的学习状态。

交付：

- 嵌入式小测和章末费曼；
- 不可变事件、版本化证据和确定性投影；
- 未验证、学习中、已掌握、待复习四种用户状态；
- 3—5 个概念的短复习任务；
- 撤销、纠正和重建测试。

验收：重复提交不重复记账；证据详情能回到原始事件和来源；删除或撤销证据后状态可重建；浏览和 Chat 不改变状态。

### M5：有证据的书内概念图

目标：概念图能解释知识关系和学习状态，而不是只展示连线。

交付：

- 当前章节与整本书两种范围；
- 受控关系类型、理由、来源和方向；
- 节点详情、关系详情和返回正文；
- 受控用户纠正；
- 手机聚焦模式和列表替代。

验收：每条可见关系能说明类型和依据；不产生无语义兜底边；用户纠正不会被再生成覆盖；状态图层不改变知识结构。

### M6：今日与学习库闭环

目标：用户每天能看到一个可解释的下一步，并管理全部学习项目。

交付：

- 一条主推荐和最多两条备选；
- 确定性排序和理由；
- 项目通知横幅；
- 进行中、已完成、已归档；
- 全书总结、归档和安全删除。

验收：推荐包含动作、原因、项目和预计时间；通知不替代推荐；学习库不出现独立原始文件行；卡片主动作与点击行为一致。

### M7：真实 HarmonyOS 端到端

目标：在目标设备上完成整条真实学习闭环。

交付：

- DevEco Studio 可构建工程；
- 连接真实 `server/`；
- 文件选择、通知、语音草稿等原生能力；
- 真机性能、无障碍、减少动态和材质降级；
- 故障恢复、日志和测试记录。

验收：`entry + server` 使用真实文件和真实模型完成“创建→首章→Chat→验证→概念状态→今日推荐”；重启应用后状态一致；失败和重试不产生重复业务事实。

## 3. 跨里程碑质量门禁

### 3.1 产品

- 页面职责符合本目录，没有新增隐形平行流程；
- 每个页面只有一个最高优先级动作；
- 用户能说明当前对象、状态和下一步；
- 资料、生成内容、补充知识和学习判断清楚区分。

### 3.2 合同

- DTO、事件和错误有版本；
- 所有写入可幂等重试；
- 客户端不解析自然语言决定业务状态；
- 服务端投影可以从事实重建；
- 服务端合同测试与 ArkTS 客户端测试使用同形夹具。

### 3.3 AI 信任

- 关键回答、关系和推荐可以查看依据；
- 模型输出经过结构验证和确定性后处理；
- 证据不足时显示不确定；
- 用户纠正有记录、影响范围和恢复方式；
- Agent 写操作需要确认。

### 3.4 交互与无障碍

- 触控目标至少 44px；
- 状态不只用颜色；
- 支持键盘、屏幕阅读和减少动态；
- 地图提供列表替代；
- 覆盖层关闭后恢复焦点和位置；
- 长任务可离开、可恢复、可重试。

### 3.5 工程

- 新增路径包含成功、空、部分成功、失败和重试测试；
- 日志不泄露资料全文、长回答和密钥；
- 真实产品表面不依赖 fixture；
- `entry/` 不复制服务端最终业务规则，`admin/` 不被当作业务事实来源；
- 合并前记录真实验证范围，禁止把 Mock 测试描述为真实模型验收。

## 4. PR 拆分建议

每个里程碑可以拆为“原型确认→合同与服务端→HarmonyOS→端到端验收”。`admin/` 用于提前确认方案，不是必须发布或长期兼容的客户端交付物。

建议顺序：

1. PR A：产品文档基线和共享合同；
2. PR B：学习项目聚合与创建状态机；
3. PR C：首章生成和单一阅读器；
4. PR D：有作用域的 Chat；
5. PR E：事件、证据、概念状态与复习；
6. PR F：有证据的书内概念图；
7. PR G：今日推荐、项目通知和学习库收口；
8. PR H：HarmonyOS 真实端到端与发布门禁。

每个 PR 描述必须列出：对应现行文档、用户可见变化、合同变化、迁移风险、已验证内容和未验证内容。

## 5. 首版明确不做

- 多资料合并学习书；
- OCR、网页、音视频和 EPUB；
- 全局跨书知识图和 Memory 工作台；
- 自由图编辑器；
- 网页搜索、MCP、Skills 和多 Agent 协作；
- 复杂预检、学习风格诊断和模型设置；
- 完整笔记编辑器、多人协作、社区、积分和排行榜；
- Android/iOS 正式客户端；
- 生产账户、计费和多租户部署。

Deferred 能力只有在单书真实闭环达到 `Verified` 后重新评审。

## 6. 完成定义

首版完成必须同时满足：

1. 一名新用户能在 HarmonyOS 独立完成完整主流程；
2. `entry + server` 对同一业务事实保持一致，并能在重启后恢复；
3. 所有生成内容、回答、关系和学习判断可追溯；
4. 中断、失败和重试不会丢失已完成工作或重复记账；
5. 今日能根据真实学习证据给出一个可解释的下一步；
6. 团队能清楚区分已实现、已接通和已真实验证。
