## 2. 文档权威关系

同一问题发生冲突时，按以下顺序执行：

1. 用户最新确认的决定；
2. 本目录对应专项文档；
3. 当前代码和自动化测试所证明的实现状态；
4. 归档材料和旧代码注释。

本目录定义目标产品语义；代码和测试说明当前实现到了哪里。代码中的旧页面、临时接口或实验行为不能反向覆盖已确认的产品定义。

仓库当前没有单独的现行视觉设计文档。视觉实现可以参考 `admin/` 原型和 `entry/` 代码，但不得改变本目录定义的页面职责、用户流程、数据事实和模块边界。

## 3. 归档边界

旧 PRD、设计规范、架构方案、API 参考、worklog 和阶段性实施计划已移入 `archive/documentation-2026-08-24/docs/`。它们只用于追溯设计与实现演进。

新增需求、接口或验收项必须写入本目录，不得从归档内容反推。需要恢复旧结论时，应先重新评审，再修改对应现行文档。

## 4. 维护规则

- 产品决定直接更新对应专项文档，并在提交说明中记录原因。
- 页面名称、领域对象和状态枚举必须引用《产品定义与术语》，各端不得另起名称。
- 文档必须区分 `Prototype`、`Integrated`、`Verified`、`Planned` 和 `Deferred`。
- 原型存在不等于需求已确认；测试通过不等于真实端到端能力已验证。
- 新增一级入口、学习证据来源、Chat 写操作或概念关系类型，需要产品与后端共同评审。
