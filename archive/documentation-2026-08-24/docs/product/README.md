## 2. 文档权威关系

同一问题发生冲突时，按以下顺序执行：

1. 用户最新确认并写入已接受 ADR 的决定；
2. 本目录对应专项文档；
3. 《产品总纲与开发路线》；
4. `MVP_SCOPE.md` 中的当前实现状态；
5. 当前可运行代码和原型；
6. 旧 PRD、旧设计稿、worklog 和归档材料。

架构决策见 [ADR-002：统一产品口径与单一学习项目闭环](../architecture/ADR-002-统一产品口径与单一学习项目闭环.md)。视觉语言继续以《视觉设计规范》和 `DESIGN.md` 为准，但视觉规范不得改变本目录定义的页面职责和用户流程。

## 3. 旧文档的处理

以下文件保留历史价值，但其中与本目录冲突的产品结构不再生效：

- `docs/PRD.md` 中“今日｜学习｜知识库”的三级导航；
- `docs/design-system/用户旅程.md` 中以独立文件理解页、单知识点深入学习页和学习地图页串联的 S01—S10 主流程；
- `docs/design-system/信息架构与页面结构.md` 中独立“学习”一级页面和全局知识地图；
- `docs/design-system/UI与交互规范.md` 中以文件列表为知识库主体、学习地图作为一级页面的交互要求；
- 历史 worklog、superpowers 方案中的阶段性页面和实验性内容块。

这些文件不删除，以便追溯设计演进。新增需求、接口和验收项不得再从旧口径反推。

## 4. 维护规则

- 产品决定先写入 ADR，再修改对应专项文档。
- 页面名称、领域对象和状态枚举必须引用《产品定义与术语》，不得在各端另起名称。
- 文档必须区分 `Prototype`、`Integrated`、`Verified`、`Planned` 和 `Deferred`。
- 原型存在不等于需求已确认；测试通过不等于真实端到端能力已验证。
- 任何新增一级入口、学习证据来源、Chat 写操作或概念关系类型，都需要产品与后端共同评审。
